# Skill 2 — 黄金帧双向回归（RTL ↔ 主机协议对齐）

## 适用场景

自定义定长帧协议（串口/SPI/总线），**RTL 侧组帧**、**主机侧解析**，两份实现必须逐字节一致。
典型的翻车点是：某一侧改了字段顺序或长度，另一侧没跟上，直到上板才发现数据全错。

不适用：标准协议栈（用现成库即可）、变长帧且无 CRC 的场合。

## 使用方法

### 1. 先写死一份「黄金帧」常量

在两侧**各自**的测试里都写同一串十六进制，来源是设计文档而不是「跑出来的结果」：

```python
# 主机侧（pytest）
GOLDEN_PASS = "55aa010126000000" + "01000200040008001000200040008000" + ... + "000000000000fffd"

# RTL 侧（verilog testbench）
localparam [383:0] GOLDEN = 384'h55AA010126000000_0100..._FFFD;
```

**关键纪律**：黄金帧一旦写下，**两侧都不得单方面修改**。要改就同时改两侧，并在提交信息里写明原因。

### 2. RTL 侧：跑一次组帧，逐字节比对

```verilog
if (frame !== GOLDEN) begin
    $display("FAIL: frame mismatch");
    $display("got %h", frame);
    $display("exp %h", GOLDEN);
    $finish;
end else $display("ok golden frame");
```

### 3. 主机侧：用黄金帧喂解析器，断言解析结果

断言的是**语义**（字段值、矩阵元素），不是原始字节，这样解析器重构也安全。

### 4. 加一条「发送途中改变输入」的回归

这一条专治**快照类缺陷**：如果发帧期间源头数据还在变，
必须保证一帧内所有字段来自**同一时刻**的快照。

```verilog
// 在帧发送进行到一半时改变矩阵
if (i == 8) matrix <= NEW_VALUE;
// 断言：整帧仍然是发送开始时的那份矩阵
```

## 失效条件

- 协议含**时间戳/序列号**等每次不同的字段 → 比对时要把这些字段屏蔽或用范围断言
- 帧长可变 → 黄金帧法失效，改用「编解码往返一致性」测试
- 两侧使用**不同的字节序约定**且未在文档中冻结 → 先补文档再谈回归

## 已验证效果

本项目的 16 通道帧（48 B）：
- 抓到一个**阻断级缺陷**：发帧时读了实时矩阵而不是快照，
  在「扫描持续重跑」的情况下，一帧 4.17 ms 内矩阵被改写约 37 次，**CRC 与负载不同源**。
- 修法：在发送触发沿锁存快照 `matrix_r <= matrix`，并补上「发送中途改矩阵」的回归用例。
- 修复后 RTL 侧 6/6 testbench、主机侧 84 项 pytest 全通过。
