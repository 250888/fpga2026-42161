# 大模型协作记录

> 按《2026 FPGA 创新设计赛道选题指南（AMD）》§3.3.3.1 / §3.3.5.3 提交。
> 记录本项目开发过程中**真实的**人机协作方式：任务如何拆、提示词怎么写、
> 模型给出过哪些**错误判断**、如何被工具输出推翻、最后沉淀成什么。

---

## 一、协作形态

不是「让模型写代码」这一种用法，实际用到四种：

| 形态 | 用在哪 | 人负责什么 | 模型负责什么 |
|---|---|---|---|
| A. 并行评审 | RTL/XDC 一致性、协议与证据、PCB 三路独立审查 | 给上下文边界、裁决冲突 | 各自出结论与阻断项 |
| B. 单点深挖 | 硬件排障、时序分析、协议设计 | 提供**实测数据**、否掉无依据的推断 | 建因果链、提下一步测量 |
| C. 工具化生成 | 报告、海报、框图、打包脚本 | 定内容口径与验收标准 | 写脚本、跑、自检、迭代 |
| D. 回归把关 | 每次改动后的 pytest / iverilog / lint | 决定红线 | 跑并如实报告失败 |

**一条硬规则**：模型不得自己宣称「通过」。所有「通过」必须由**本次会话实际运行过**的命令输出来支撑。

## 二、智能体工作流设计

### 2.1 并行评审的上下文隔离

三路评审**互不共享会话**，各自只看自己那一份材料：

```
评审1（RTL↔XDC）：只给 rtl/ + constrs/ + 端口清单
评审2（协议与证据）：只给 protocol.py + uart_packet_tx.v + 帧规范
评审3（PCB）：只给 pcb/frontend16/ 生成脚本 + DRC 报告
```

**为什么隔离**：共享上下文会让三路收敛到同一个视角，失去交叉验证价值。

**代价**：三份结论可能互相矛盾，需要人来裁决。本项目裁决过一次——
评审2 认为「帧矩阵未快照」是阻断，评审1 认为不影响功能正确性。
最终按「帧内字段必须同源」这条更严的标准判为**阻断**，事实证明是对的。

### 2.2 单点深挖的「数据驱动」约束

排障过程中定了一条纪律：**模型每提一个假设，必须同时给出可判真伪的测量**。

反例（本项目早期真实发生）：

> 模型：「3.8 kΩ 说明外扩板 VCC 轨漏电。」
> 人：量了「拔掉板间排线后的同一测试点」→ 开路。
> 结论：3.8 kΩ 是主控板电源轨的正常阻抗，**假设被推翻**。

这条纪律的价值在于：**假设可以被一次测量杀死**，而不是靠争论。

### 2.3 工具化生成的自检闭环

生成类任务（报告 / 海报 / 框图）的固定流程：

```
写生成脚本 → 跑 → 渲染图 → 看图 → 发现问题 → 改脚本 → 重跑
```

**关键**：模型必须**真的看图**，而不是相信脚本没报错。
本项目海报第一次生成时脚本零报错，但渲染出来标题压住了区块标题条。

## 三、自我纠错轨迹（六次）

### 3.1 帧矩阵快照（阻断级，被并行评审抓到）

| 阶段 | 内容 |
|---|---|
| 现象 | 帧内 CRC 与负载偶发不一致 |
| 模型初判 | 「CRC 实现有误」 |
| 推翻方式 | 打印帧组装过程中的矩阵值 → 发现一帧 4.17 ms 内矩阵被改写约 37 次 |
| 根因 | 发帧时读**实时**矩阵，而扫描在持续重跑 |
| 修法 | 发送触发沿锁存快照 `matrix_r <= matrix`；补「发送中途改矩阵」的回归用例 |
| 沉淀 | → `skill/golden-frame-regression.md` |

**教训**：模型第一反应往往是「算法写错了」，而真实原因是**数据在动**。

### 3.2 电源轨漏电误判

| 阶段 | 内容 |
|---|---|
| 现象 | 外扩板 VCC 对地 3.8 kΩ，怀疑漏电 |
| 模型初判 | 「板上有短路，逐个隔离器件」 |
| 推翻方式 | 拔掉板间排线后同一测试点**开路** |
| 根因 | 板上有 0 Ω 电流断点直连主控板，量到的是**两块板并联**的阻抗 |
| 沉淀 | → 踩坑清单判据 D |

### 3.3 虚焊 vs 断线的混淆

| 阶段 | 内容 |
|---|---|
| 现象 | 某通道蜂鸣档「通」，但系统读不到 |
| 模型初判 | 「通路正常，应该是芯片坏」 |
| 推翻方式 | 量同一网段两端电压：一端 3.3 V、另一端 0.3 V |
| 根因 | 蜂鸣测的是**焊盘**，引脚与焊盘之间虚焊 |
| 沉淀 | → 踩坑清单判据 C |

### 3.4 局部补焊制造新故障

| 阶段 | 内容 |
|---|---|
| 现象 | 补焊两脚修好了 1 路，却弄坏了相邻 2 路 |
| 模型初判 | 未预警 |
| 原因 | 0.65 mm 脚距，局部加热使邻脚焊锡软化位移 |
| 修法 | 改为整排一次拖焊 |
| 沉淀 | → 踩坑清单判据 E |

### 3.5 报告渲染「截断」的假警报

| 阶段 | 内容 |
|---|---|
| 现象 | 转 PNG 预览后正文右侧被切掉 |
| 模型初判 | 「插入段落没挂样式导致字号偏大」 |
| 部分正确 | 确实有样式问题，修了 |
| 创新发现 | 修完仍截断 → 用**原模板**渲染对照，**原模板同样截断** |
| 结论 | 是字体替换的渲染假象，Word 中正常，**不是文档缺陷** |
| 沉淀 | → `skill/report-templating.md` 第 3 节 |

**教训**：怀疑自己引入的缺陷之前，先做一次「原样对照」。

### 3.6 作品名来回（流程教训，非技术）

| 阶段 | 内容 |
|---|---|
| 事件 | 作品名在「瞬迹 / 瞬狙」之间改了一次又改回 |
| 代价 | 报告标题、参考文献、上位机界面、包名、包内目录、GitHub 提交全部重做 |
| 根因 | 名字级信息没有在建档时与队长一次性确认 |
| 纪律 | **口径类信息（名称/口径/提交格式）必须先书面确认再动手** |

## 四、有效的提示词模式

### 4.1 「给实测数据，不要给判断」

✓ 有效：

```
这是串口抓到的帧：cls=1 open=0x0020 stuck=0x0000 connections=15
拔掉的是 A5↔B5 那根线。分析系统判定是否合理。
```

✗ 无效：

```
板子好像有点问题，你帮我看看
```

后者会让模型输出一大串不可证伪的可能性，浪费一轮。

### 4.2 「先给约束，再给任务」

有效：

```
约束：
1. 不得改动 RTL 的端口集合（XDC 已冻结）
2. 报告里不得出现学校名/队名/队员
3. 不引用未经示波器实测的脉宽数值
任务：...
```

把**不可协商的边界**前置，比事后纠正便宜得多。

### 4.3 「要求给出可反驳的判据」

有效：

```
说「这里到顶了」之前，先说明「如果出现什么现象就说明我错了」。
给不出可反驳判据的，只说「当前数据不足以判断」。
```

这条纪律实际拦下过一次错误结论（把某指标的局部回落判成「饱和」）。

### 4.4 「交付前用工具自证」

有效：

```
不要说你完成了。跑命令，把输出贴给我。
```

模型的自我评估不可靠，但**命令输出**可靠。

## 五、模型判断失误的清单（如实记录）

| # | 模型说了什么 | 实际 | 发现方式 |
|---|---|---|---|
| 1 | 「CRC 实现有误」 | 数据在动，不是算法 | 打印中间值 |
| 2 | 「外扩板电源轨漏电」 | 量的是两块板并联阻抗 | 拔排线复测 |
| 3 | 「蜂鸣通就是通路好」 | 焊盘通 ≠ 引脚通 | 量网段两端电压 |
| 4 | 「报告右侧截断是你引入的」 | 原模板同样截断 | 原模板对照渲染 |
| 5 | 「7-Zip 可以生成 RAR」 | 7-Zip 只能解压 RAR | 查格式能力表 |
| 6 | 「把模板页复制一份做英文版」 | python-pptx 1.0.x 复制页丢图片关系 | 渲染后发现图没了 |
| 7 | 「就近补焊两个脚就行」 | 会祸及邻脚 | 补完反而多坏两路 |

**共性**：失误集中在**「没有实测支撑的因果推断」**和**「库能力想当然」**两类。
对应的防线就是本文 4.1 与 4.4 两条纪律。
